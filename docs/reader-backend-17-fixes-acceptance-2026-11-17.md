## 首轮遗漏证据（现已修复）

### F01 · 已修复 · 原 P1 · 已取消的新协议遮蔽仍可续费的旧协议（R04）

**位置**：`reader-backend/internal/wallet/repository.go:412-421`，`wallet/handler.go:377-399`，`reader-front/src/pages/Recharge.tsx:395-415`。

管理查询依旧 `ORDER BY id DESC LIMIT 1`，候选既包含 ACTIVE 等可管理协议，也包含仍有已付费权益的 CANCELLED 协议。历史账号若有旧 ACTIVE 协议，以及较新但已取消、付费期未结束的协议，接口只返回新 CANCELLED。充值页又不为 CANCELLED 显示取消按钮，因此旧协议的 ID 与取消入口继续被隐藏。

**复现**：插入同账号两个协议：旧 ACTIVE 的本地付费期已过，新 CANCELLED 的已付费期还有 20 天；调用真实 Repository，返回 `I-NEWER-CANCELLED`，旧 `I-OLDER-ACTIVE` 不出现在响应中。是否再次扣款由真实渠道决定，本次没有模拟成“已发生扣款”。

**影响范围**：历史重复协议账号。新建协议的串行化保护降低了新增重复概率，但不能作为历史协议已全部可管理的证明。

**建议**：返回全部本人可管理协议，并将 paid entitlement 独立返回；界面逐项管理。仅把 ACTIVE 排在前面仍不足以处理多个历史 ACTIVE。

**补充验收**：旧 ACTIVE + 新 CANCELLED、新 PENDING + 旧 ACTIVE、多个 ACTIVE，均能看到每个仍可能扣款协议的取消入口；已付费权益不会因管理排序改变。

### F02 · 已修复 · 原 P2 · 默认套餐继承导致推广身份和像素丢失（R09，关联 R14）

**位置**：`reader-backend/internal/wallet/checkout.go:64-72`，特别是第 70 行的 `WHERE recharge_template_id IS NOT NULL`；`cms-backend/db/schema.sql:817`。

“推广身份是否存在”被错误地与“是否显式指定套餐”绑定。合法链接可以配置像素、同时让套餐继承系统默认。用户虽然已绑定该推广 ID，但创建订单的 LATERAL 查询会过滤掉它。套餐仍由 COALESCE 正确选择默认值，订单创建成功，却把 promotion_link_id 和 metadata.pixel_id 写成 NULL。结算生成的 outbox 为 unattributed，不进入正常投递队列。

**复现**：默认套餐可用、用户绑定推广 ID、推广有像素而 template 为 NULL。调用真实 `CreateCheckout` 成功；查询订单两项归因字段为 NULL。将订单置为成功履约后，真实触发器产生 unattributed 事件。

**建议**：始终解析推广身份；套餐仅作为独立字段继承默认值。报价、整本适用范围、归因和像素应复用同一解析结果，不能因继承套餐而丢弃推广记录。

**补充验收**：有/无显式套餐 × 有/无像素的组合；默认套餐下仍保存原推广和像素，已配置像素的合法推广收款不能成为 unattributed。

### F03 · 已修复 · 原 P2 · 历史已收款订单状态回退会再次生成 Purchase（R14）

**位置**：`cms-backend/db/schema.sql:820-831`；真实退款失败恢复路径见 `cms-backend/internal/billing/refund.go:410-430`。

事件触发器在任意 INSERT/UPDATE 后，只检查 NEW 是否为 Success/Paid、已履约且非已退款报告，没有限制为首次结算/首次履约或明确纳入 outbox 的订单。上线前已由旧内存路径发送过 Purchase 的近期订单没有 outbox 去重记录。退款失败从 RefundPending 恢复原 Success 时，会创建新 ID 的 Purchase，尽管没有新收款。旧事件使用时间戳 ID，新 ID 是 `payment:<order>:Purchase`，不能假设两者可被渠道去重。

**复现**：在临时库构造“上线前成功履约、没有 outbox 记录”的订单，再执行 RefundPending → Success；结果新增一条 pending Purchase。构造历史行时仅在临时库关闭并重新启用触发器，没有修改生产或仓库 schema。

**影响**：可能重复计算广告转化及收入；不是重复扣款，也不是本次真的向 Meta 发出了重复事件。

**建议**：区分原始结算/履约状态推进与退款失败恢复，明确 outbox 切换边界及历史补发策略。旧订单普通 UPDATE 不应隐式成为补发入口；也不能简单只允许 INSERT，否则会漏掉先 Pending 后结算的正常订单。

**补充验收**：历史已发事件订单退款失败恢复、备注更新不再生成新 Purchase；新订单 Pending → Success、同事务回滚、周期待复核后履约仍正确产生一次事件。
