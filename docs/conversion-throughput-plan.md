# 回传链路吞吐优化方案：同 Pixel 每请求最多 100 条

2026-11-23。适用于 Star Novel Reader、Conversion Worker、Meta CAPI、CMS 对账和监控。实施基线为 `codex/payment-domain` 的 `5ec1513` 加评审时的未提交改动。本文确定 R04–R06 的最终实施方向，验收数字均为拟定目标。

## 1. 交付目标与容量预算

**同一环境、同一 Pixel 每次发送 1–100 个已就绪事件。** 有积压时尽量装满，低流量时第一条即可发送。首版保留每 Pixel 同时最多 1 个请求、两次请求发起至少间隔 3 秒、每环境最多 5 个在途请求。100 是本系统的请求上限。Meta 的批量接口接受同 Pixel 事件数组，官方上限为每次 1,000 条，并建议尽快发送。 [Meta CAPI 批量接口](https://developers.facebook.com/documentation/ads-commerce/conversions-api/using-the-api#batch-requests)

| 需要回答的问题 | 首版验收目标 |
| --- | --- |
| 发送端能否排空热点积压？ | 预置同 Pixel 1,000 条合法投递，全部已就绪。模拟每次响应 2 秒、无拒绝时，应为 10 个请求，理想约 29 秒全部确认；含数据库操作的隔离测试目标 ≤35 秒。 |
| 上游能否供得上？ | 从同一时刻已提交的 1,000 条 Reader Outbox 开始，单 Pixel、全部命中、一条源事件对应一条投递。以最后一条原目标确认落库为终点，首版目标 ≤60 秒。记录每阶段耗时及实际批次数，小批提前发送可能超过 10 次。 |
| 低流量会不会变慢？ | 空队列、Pixel 无冷却且有可用槽时，单笔付款从 Outbox 提交到发起 HTTP 的 P95 ≤1 秒（隔离目标）。有积压或冷却时单独统计。 |
| 持续放量是否稳定？ | 按实际峰值和扇出回放至少 30 分钟，再以峰值的 1.5 倍做容量试验。记录能持续承载的入队速率；目标负载下就绪队列最老年龄不持续增长，无因调度饥饿而到期的投递，核对业务请求 P95 与上线前基线。 |

设平均每批有 B 条，从一次 HTTP 开始至结果提交、释放槽位用时 S 秒。忽略领取和准备间隙，单热点的发送上限约为 `60 × B / max(3, S)` 条目标投递/分钟。B=100、S=2 时为 2,000 条/分钟；S=4 时为 1,500 条/分钟。1,000 条都已就绪时，末批确认耗时近似 `9 × max(3, S) + S`。**2,000 是满批发送上界，端到端容量还取决于上游归一化、数据库写入、扇出、重试和批次装载率。** 容量规划按各 Pixel 的目标投递数换算；例如每笔付款产生两类事件且各投两个 Pixel，100 笔付款最多产生 400 条初始投递。

## 3. 从业务提交到投递就绪

1. **业务事务只负责可靠入队。** 保留注册、结账、付款的稳定业务键，以及资格快照和 Outbox 同事务提交。支付请求线程不调用 Meta。对批量导入和重放继续按业务键去重。
2. **Reader 和分销 Inbox 各自连续消费。** 使用现有按行锁定及事务消费入口。每次取得满批工作量立即续领；单轮时间预算耗尽但已有进展时尽快续跑。空队列先短等待并逐步退避，首版将空闲探测上限设为 250 毫秒作为压测起点。心跳、到期扫描保留独立节奏；数据库错误使用有界退避，避免失败时空转。也可用事务提交通知提前唤醒，定时探测负责兜底。
3. **先提高消费占空比，再按实测增加并行度。** 归一化批量参数控制一次循环的工作量；每条消息继续单独提交。保留账户授权、原目标、付款策略及同付款 Purchase/Subscribe 共享决策的锁和唯一键。扩大并行度前验证推广链规则序号、首单证据、重复消费与补建。Reader 和 Inbox 分配独立消费预算，防止一方积压饿死另一方。
4. **给数据库留出发送与恢复容量。** 当前每进程数据库池上限 8。先测归一化每秒成功数、连接获取等待、热点付款锁等待与慢 SQL，再确定并发和池大小。批量读取发送载荷、批量写尝试和回执，避免一个 100 条请求带来 100 次串行读写往返。使用代表性积压上的执行计划验证待发索引能支持按环境、目标、就绪时间和 ID 小范围领取。

### 分销正式上线时的消费者配置

按 Reader 与 Partner 同时承载业务流量规划。建议从 **2 个 Worker 实例，每实例 Reader 2 个、Partner Inbox 2 个**开始生产等规模压测。集群合计 Reader 4 个、Partner 4 个；一个实例重启期间，两路仍各有 2 个消费者。此配置是待验证的容量起点。

| 参数 | 每实例起始值 | 两实例合计 |
| --- | ---: | ---: |
| Reader 归一化消费者 | 2 | 4 |
| Partner Inbox 归一化消费者 | 2 | 4 |
| Worker 数据库连接池上限（建议改为可配置） | 16 | 最多 32 个连接 |
| 单消费者每轮最多处理消息数 | 20 | 两个来源分别持续消费 |

当前每路并发支持 1–3，测试环境每实例合计最多 4，故可先用双实例验证 2+2。连接池目前固定为 8；实施时将 Worker 池上限独立配置，并将两个 Worker 的 32 个连接与其余服务、运维预留一起计入 PostgreSQL 总预算。当前仅测试环境挂载司南模拟适配器；正式接入须接通正式契约、鉴权和 Inbox 消费注册，并对实际启用的两路统一校验并发预算。 [启动与配置](../conversion-backend/cmd/conversion/main.go)

**按实测决定是否继续加 Partner。** 在 Reader 峰值同时存在时，分别采集 Partner 高峰每秒持久化入队数、每秒归一化提交数、最老待消费年龄及数据库连接与锁等待。用实际应用、推广链、重复回调和目标扇出分布持续回放 30 分钟，再按 1.5 倍预测峰值回放。稳态两路最老等待年龄应无持续增长；注入突发后记录清空时间，并单独演练一个实例重启。若 Partner 持续积压而数据库还有余量，测试每实例 Reader 2、Partner 3（集群 4+6），同时调整现有合计上限。若瓶颈出现在同一付款或推广链锁、Meta 就绪队列或分销回告队列，应分别处理相应阶段。

## 4. 同 Pixel 批次如何领取与发送

- **请求占槽。** 在现有环境级领取协调下，选最早有可执行任务的合格目标，预留一个请求槽和一个目标租约。在短事务内按稳定顺序锁任务，选同环境、同目标、同一有效凭据版本的最多 100 条。将活动上限统计、下次可领时间和租约扫描全部改为按活动请求计算。5 个全局槽可对应最多 500 条在途成员。数据库事务在 HTTP 前释放。
- **两级公平。** 多个可领 Pixel 按等待时间轮转，限流目标不占可用发送槽。同 Pixel 保留支付优先和超龄任务提升优先级；两类持续就绪时，用现有连续支付计数按成员分配名额，跨批保存。避免一批 100 笔支付只被算作一次支付领取。某类不足时，其余名额立即给另一类。
- **预检后冻结实际成员。** 逐条校验截止时间、匹配字段、金额、事件名、授权和付款决策。本地坏行单独定稿或阻塞，其余继续成批；同一请求内确保每个事件名与 Meta event_id 组合唯一。发送前在数据库复核租约、凭据及最新冷却时间，原子记录真正发出的成员和发送边界。凭据已轮换则重新准备。以实际开始发送时间推进 Pixel 间隔，避免准备耗时造成两次 HTTP 紧邻。没有合法成员时直接释放槽。
- **唤醒与限流。** 一个批次完成就补一个槽；冷却到期时及时补发。新就绪任务可用通知或有界短轮询唤醒空闲发送器，以满足单笔延迟目标。明确限流时，在完成事务内持久化 Pixel 冷却，使用现有截止时间与有效 Retry-After / 有界退避中的较晚者；其他实例同样遵守。单纯传输超时保留结果未知。首版维持现有请求超时，若高装载批次频繁接近超时，先按实测缩小批量并核对租约余量。
- **配置。** 新增建议参数 `CONVERSION_META_BATCH_SIZE`，允许 1–100，灰度从 1 调到 10、50、100。复用现有每环境全局并发、进程并发、Pixel 间隔和归一化批量参数。批量取 1 走同一条正式路径。

## 5. 回执、去重与故障恢复

以请求批次保存环境、目标、凭据版本引用、租约令牌、开始时间、发出成员数、响应时间、HTTP 状态、Graph 错误、接收总数及 trace。以现有 delivery attempt 关联批次及成员位置，保留稳定 Meta event_id、尝试次数和逐条结论；对同一批次的成员与位置分别加唯一约束。历史单发记录允许没有批次。审计和 CMS 展示批次摘要及脱敏关联，不存 Token 或重复保存用户匹配原文。

| 返回或故障 | 处理 |
| --- | --- |
| HTTP 200、无 Graph 错误、接收数等于实际发出数 | 先耐久化批次回执，再以同一冻结成员集幂等定稿。每笔成功通过批次引用取得证据，CMS 可见“本请求接收 100/100”。SQL 约束、诊断恢复和分销回告均要识别批次证据；历史单发证据继续走原判断。 |
| 接收数 99/100、空回执、含糊错误、发送后超时 | 保存原始结构化计数。没有可定位的逐条证据时，未能确认的所有成员进入结果未知，不猜测哪一笔失败，也不自动拆批重发。人工恢复继续执行现有重复风险确认、期限及预算校验。 |
| 明确整批零接收的限流或瞬态拒绝 | 分别按原预算、截止时间重排；限流同步推进目标冷却，普通瞬态错误仅按重试计划处理。批次含有部分接收迹象时按未知处理，独立记录限流信号。 |
| 参数错误或授权失效 | 仅在有明确整批零接收或逐条定位证据时归类。凭据错误按目标阻塞；对于已证实零接收且疑有坏行的批次，可有界二分隔离，拆分也计入尝试预算。无法证明零接收时保留未知。 |
| 崩溃、完成事务失败或旧租约响应迟到 | 发出标记前失租可重新领取；已标发出而缺确认进入未知。有耐久化完整回执时，恢复进程只重放本地定稿。以批次令牌和成员尝试号防止过期写覆盖新状态；迟到证据留档。原目标定稿与分销回告入队沿用同事务和唯一键。 |

原有 `events_received=1` 约束、`confirmedEvidenceTx` 和回告载荷都隐含单事件语义。迁移时明确分开“批次实际接收总数”和“本投递已由完整回执确认”；禁止把批次总数复制成每条的接收数后累加。批次和成员证据的保留期应覆盖所有尚待恢复的成员。司南发送回告仍使用独立队列与契约；在模拟环境压测其积压和回告延迟，必要时将回告 Worker 改为槽位释放即补位，避免等待下一轮 15 秒扫描。 [分销回告 Worker](../conversion-backend/internal/partner/report_worker.go)

## 6. 测量、验收与上线顺序

**用三个时间点定位瓶颈。** 取源消息成功入队、目标投递就绪、Meta 确认落库，并另外记录 HTTP 开始、响应时间。按环境、来源、事件类型和热点 Pixel 分别展示每秒入队、归一化、就绪、确认量，P50/P95/P99 延迟、队列最老年龄、到期数。HTTP 维度展示请求量、平均及分位批大小、429 率、未知批次数和受影响投递数。付款覆盖率继续按付款去重，原目标成功率按事件去重。Collector 跟踪两段积压趋势、未知数突增、持续限流及最近成功采样时间。

| 隔离验收 | 必须核对的结果 |
| --- | --- |
| 同一批工作负载按批量 1、10、50、100 运行 | 固定数据库资源、3 秒间隔和模拟延迟，记录实际请求数、全链路确认耗时、数据库往返与锁等待。60 秒端到端目标从 Outbox 计时；源消息数、生成投递数、各终态与仍在途数能逐笔对平。 |
| 冷启动单笔、跨批边界、混合负载 | 测 1、99、100、101 和 1,000 条；已有积压时 101 条拆为 100+1，最后 1 条按下个可发窗口发送。多 Pixel、双实例、支付持续进入以及多目标扇出下，冷门目标和非支付事件仍获机会；每目标同时最多一个请求。 |
| 错误与恢复 | 注入 429+Retry-After、部分计数、凭据轮换、过期单行、网络超时。在发送边界前后、收到回执后落库前后杀进程。验证正确冷却、完整证据恢复、未知留待核对、无重复定稿或重复回告。 |
| 业务回归 | 验证白名单、退役前冻结归因、策略跳过、Purchase/Subscribe 共用决策、人工重排与 CMS 逐单对账。重放同一 Outbox 或 Inbox 后核对计数与稳定 ID。分别统计本地失败、明确媒体拒绝和结果未知。 |

**实施顺序**：先记录当前工作区版本的基准，并交付归一化连续消费和分段指标；随后由 CMS 正式迁移添加请求批次、成员关联、受限角色授权及索引，同步各服务 schema 门槛。以批量 1 验证新协议全链路，包括原目标回告和诊断恢复。替换调度协议时先暂停旧发送器、等待在途完成或按旧语义恢复，再启用新发送器，避免两套租约算法同时占槽。通过隔离验收后，在选定 Pixel 或隔离环境按 10、50、100 放量，每档比较确认率、未知率、限流、业务延迟和最老积压。

若未知结果、到期或重复回告增加，暂停扩大流量，将新领取批量降至 1；已发出的批次继续由新版按原成员恢复。涉及二进制回退时先停止新领取，排空并核对在途批次，选择能读取新增账本和当前 schema 的兼容版本。保留既有回执与稳定事件键，避免回退触发媒体重发。
