## 3. 待处理问题

### N01 · P1 · OSS 正文覆盖与数据库版本不能原子发布（关联 R13）

**位置**：`cms-backend/internal/novel/service.go:521-535,574-592,805-865`；固定对象键 `reader-backend/internal/storage/oss.go:72-88`；Reader 缓存 `internal/novel/service.go:215-241`。

CMS 在持有数据库事务及小说/章节写锁时，把新正文写到同一个 `novels/<id>/<index>.txt` 对象，然后才提交数据库。批量导入同样先删除/重建数据库章节，在事务内批量覆盖 OSS。数据库回滚不会撤回已完成的对象覆盖。

**复现**：真实 CMS Repository/Service + 隔离 PostgreSQL + 模拟 OSS，注入 Commit 失败。结果数据库章节仍是 `Old title`，OSS 已是 `NEW OBJECT`，版本号在覆盖期间及回滚后均为 `2`。因此读者可以在旧版本命名空间读取并缓存新正文；事务最终失败后也没有版本推进来修复它。批量上传部分成功后失败同理。长 OSS IO 还会长期占用数据库连接和写锁。

**方案**：改为不可变正文对象键（章节稳定 ID + 内容 hash/修订号）。先在事务外上传并校验全部对象，再用短事务原子更新正文引用、字数及发布版本。失败只留下待清理的未引用对象；已发布引用始终指向完整旧对象。回收旧对象采用可追溯异步任务，并保护并发新发布。不能只调整“清缓存”的时机，也不能把可变对象写操作简单移到事务外。

**验收**：覆盖上传失败、部分成功、Commit 失败、读写交错、两次并发导入及清理交错；正文 hash、字数、计价元数据与版本始终匹配；失败发布不改变线上正文。

### N02 · P1 · 全量重导入改变章节索引后，已购权益会转移

**位置**：`cms-backend/internal/novel/service.go:804-840`；`cms-backend/db/schema.sql:143-152`；`reader-backend/internal/novel/repository.go:230-249`、`cache.go:124-155`。

导入删除旧章节并为所有新章节重新生成 ID；购买记录和 Redis 解锁集合却按 `(user_id, novel_id, chapter_index)` 保存。插入前言、调整章节顺序或重分章后，相同 index 可能已是另一个章节。内容缓存版本化不会修复权益索引。

**复现**：用户已购 index=2；重导入把原章节移到 index=3，并在 index=2 放入不同内容。实际 Repository 判断：不同内容仍已解锁，原购买章节反而未解锁。读者可能被要求再次付费，也可能获得未买章节。

**方案**：把购买对象建模为稳定 chapter_id，章节排序独立保存；编辑/导入保留已有章节身份。用发布 staging 和显式映射处理移动/拆分，历史记录迁移需可审核。重建用户权益缓存并版本化其映射；不能通过删除旧解锁记录“修复”。并发解锁应核验其购买的稳定章节/报价版本。

**验收**：插入前言、移位、删章后恢复、重命名、拆分、重复标题、导入与扣费交错；已有购买不能无提示失效或转给其他内容。

### N03 · P2 · CMS 小说级 0 单价仍被保存为继承（关联 R08）

**位置**：`cms-backend/internal/novel/service.go:283-285,338-340`。

Reader 已使用 COALESCE 保留 0，但 CMS CreateNovel/UpdateNovel 将 `coinCost <= 0` 改为 nil。全局及推广设置明确接受 0，小说级写路径却不一致。

**复现**：调用真实 UpdateNovel Service，传入非 nil 的 0；返回及持久化模型的单价为 nil。全局非零时，小说继承非零价而非免费。探针复用了仓库的 fake Repository，不发真实外部请求。

**方案**：三层统一 NULL=继承、0=免费、负数=非法；CMS 表单、绑定、Service、批量操作均保留该语义。若产品禁止小说级免费，应明确 4xx 拒绝，不能静默转换。

**验收**：经 CMS 正式 Create/Update/批量接口写入 NULL、0、正数，再核对 Reader 目录、正文及实际扣币；不能只直接 INSERT 数据库来验收。

### N04 · P2 · 账号输入契约大于数据库列，合法绑定请求落为 500

**位置**：`reader-backend/internal/auth/handler.go:115-118,168-170`、`repository.go:37-72`；`cms-backend/db/schema.sql:43-54`。

Handler 接受邮箱最多 255、昵称最多 100，数据库分别仅 100、50。游客把原始 User-Agent 直接写入 VARCHAR(255) 的 device，也没有与存储一致的约束。

**复现**：实际 Gin Handler + PostgreSQL：51 字符昵称、112 字符合规邮箱均通过绑定后返回 500（SQLSTATE 22001）；256 字符 UA 使游客创建失败。事务回滚且未泄露 SQL 错误，但可用性问题依然存在。

**方案**：统一所有入口及存储的长度。邮箱可评估扩列并明确规范化策略；昵称按产品长度严格 400；device/UA 等诊断字段按已明确策略截断或独立 TEXT 保存，不能阻断游客登录。UTM 等来源 header 同样检查存储边界。同步纠正上一轮文档中与数据库不一致的上限。

**验收**：注册、绑定、游客、Unicode、边界值和超长来源 header；有效输入可落库，非法业务输入为可读 4xx，诊断字段过长不阻断身份创建。

### N05 · P2 · Redis 默认选项不能保证请求截止时间（关联 O01）

**位置**：`reader-backend/internal/redis/redis.go:15-35`；当前依赖 `go-redis/v9 v9.21.0` 的 options.go/redis.go。

buildRedisOptions 没有设置 ContextTimeoutEnabled。当前依赖默认 false，socket IO 使用 background context；默认读超时 3 秒、MaxRetries=3。仅给 HTTP 请求加 WithTimeout，不能让这些 socket IO 按较早截止时间中止。慢缓存可能拖过健康检查/普通请求预算，并挤压后续数据库回源时间。

**复现**：本地 RESP 模拟服务器，使用应用选项构造逻辑；缩短 socket ReadTimeout 至 200ms、禁用重试以隔离变量。传入 20ms 截止时间，实际约 200.94ms 才返回 IO timeout，ContextTimeoutEnabled=false。没有连接真实 Redis。

**方案**：显式启用并测试 context deadline；为缓存设置短的连接/读写/连接池等待/总尝试预算及较少重试。正文缓存故障回源需预留 DB 时间和并发上限，避免所有调用同时回源；健康检查使用自身严格预算。不能仅把单次 socket timeout 调成 10 秒来匹配 HTTP。

**验收**：慢响应、连接池耗尽、重试、父 context 取消、缓存短暂故障及恢复；端到端耗时不超过接口预算，回源量有界。

### N06 · P2 · 同版本 CMS 重启仍跑全量事务 DDL，能阻断 Reader（关联 O04）

**位置**：`cms-backend/internal/db/postgres.go:54-85`；`cms-backend/db/schema.sql` 的 ALTER TABLE/DROP、CREATE TRIGGER。

版本相等时没有跳过迁移，仍在一个事务里重跑完整 schema。DDL 锁保留到 seed、序列修复和最终 Commit 完成。advisory lock 只串行 CMS 迁移，不保护 Reader 的正常 SELECT。

**复现**：隔离库先完成迁移，第二次运行相同版本；用另一个事务阻塞后续 transactions 表操作。第二次迁移已经持有 novels 的 AccessExclusiveLock，Reader 的 SELECT 在 100ms 截止时间内超时。阻塞解除后迁移完成。不是声称正常每次重启都会耗时 100ms 或必然造成线上事故。

**方案**：真正按不可变版本迁移执行且只执行一次；同版本启动只做兼容检查。把发布迁移与每个进程启动解耦，设 lock_timeout、DDL 时长及失败回退。需要 CONCURRENTLY 的索引必须由事务外专用发布步骤完成；不能放入现有整块事务。不要删除失败退出和 ready 门槛。

**验收**：同版本重启无业务表 DDL 锁；多实例迁移串行且只执行一次；老 Reader 有流量时可控发布；失败后 ready 保持失败，重试不重复危险操作。

### N07 · P2 · 进度发送失败前已出队，没有持久重试

**位置**：`reader-front/src/App.tsx:333-340,545-553`。

定时同步在请求成功前删除 pending 项；失败只打印日志。页面隐藏发送则先清空整个 pending 表再调用 keepalive，catch 为空。状态没有持久化为待发送队列；恢复网络或页面刷新后没有该更新可重试。上一轮分批只解决单次大小，不能保证失败恢复。

**方案**：以用户 ID + novel ID 保存持久 pending outbox（合并最新时间戳），收到成功确认后仅删除已确认版本；失败保留、退避，并在恢复网络/登录后重试。请求成功期间若又产生更新，不得删掉新版本。退出发送仍属尽力而为，不能依赖它替代已持久化的队列。

**验收**：离线、503、部分批次成功、发送中新进度、页面重开、切账号和多标签；恢复后只提交所属账号的最新记录。此项为代码路径确认，未跑真实浏览器退出实验。

### N08 · P2 · 未收藏小说的已保存进度没有正常恢复入口

**位置**：`reader-backend/internal/shelf/repository.go:25-36,119-128`；`reader-front/src/App.tsx:153-175,634-638`。

SaveProgress 新建行时 in_shelf=false；获取书架只返回 in_shelf=true。H5 却仅从书架返回值重建 readingProgress，没有独立读取阅读历史/指定小说进度的调用。用户不收藏直接阅读，或移除收藏后再打开无章节参数的入口，会丢失恢复依据。

**复现**：保存小说 index=8、offset=0.6 后，GetProgress 能读到记录，GetShelfItemsWithNovel 返回 0 条。书架是否收藏和是否有阅读进度是两个不同维度。显式 chapter_index URL 可能保留章节号，但不能替代正文偏移及跨设备恢复。

**方案**：保留当前书架筛选语义，新增按本人小说查询进度/分页阅读历史的正式接口，阅读页启动时加载并与本地待同步版本合并；不要为了取进度把全部历史读物当成收藏。

**验收**：未收藏阅读、移除收藏、重启页面、跨设备、显式章节链接优先级；进度存在时可恢复且不改变收藏状态。

### N09 · P2 · CMS 相关查询仍忽略迭代故障，并有配置错误静默回退

**位置**：`cms-backend/internal/novel/repository.go:94-101,418-433` 及其余 rows 循环；`service.go:765-785`。

Reader 的 O03 修复完整，CMS ListNovels/GetSettings 等循环仍未检查 rows.Err。BulkImportChapters 又忽略 GetSettings 返回错误，使用 500/3 等默认值。查询中途失败可以成为“成功的部分配置/列表”；数据库不可用也可能被当成“未配置”。

**影响界定**：CMS 显示及导入计价元数据可能错误，且发布无法可靠失败；这不是本轮已经复现 Reader 实际错扣金币的结论，Reader 仍重新读取有效定价。

**方案**：CMS 对应 Repository 完整检查迭代错误，Service 区分配置缺失与读取失败，只有明确缺失才应用默认；错误时不继续发布或批量改价。

**验收**：注入 Scan/rows.Err/数据库连接错误，配置必须整体失败；验证未执行后续写入。此项为静态代码证据，没有做网络断连式 rows.Err 注入。

## 4. 阅读消费的性能和高并发建议

2026-11-17 后续实现与隔离验证见 [阅读性能优化验收](reader-performance-acceptance-2026-11-17.md)。下文保留审查时的依据和原始建议。

### P01 · 先降低热路径数据库往返，而非直接提高连接池

在缓存命中、登录、付费章节场景，当前约需要：VIP 4 次 SQL，非 VIP 已单章购买/整本权益 5 次，未解锁预览 6 次；分别包含账户/会话、小说版本、定价、VIP、整本及按需解锁索引查询。匿名预览也至少查版本和定价。次数按当前 Service 调用链静态计算，不是压测结果。

优先补 SQL 专项的有效期索引，再把账户状态、有效定价、发布版本及权限 EXISTS 聚合为一个请求级 ReadContext，避免模块间重复查权和网络往返。正文缓存保持共享、权限结果保持用户隔离。退款、封禁、下架的及时生效语义必须保留；不能用长 TTL 正权限缓存掩盖数据库负载。

### P02 · 将章节元数据/预览与完整正文分离

当前 service.go:215-252 在鉴权前回源并缓存完整正文。大量未购买预览或随机章节访问也会读取完整 OSS 对象、反序列化整篇内容并占用 Redis。建议发布时生成不可变短预览；先查元数据和权限，未授权只读预览，授权后再取全文。正文 API 明确私有缓存策略；若引入 CDN，必须单独设计付费授权，不能公开缓存按 URL 区分的完整正文。

### P03 · singleflight 需要独立的加载生命周期和可取消等待

service.go:119、159、219、314 使用同步 Do，闭包捕获首个请求 context。首请求取消会拖累同组调用；等待者不能按自己的截止时间退出。探针确认：10ms 截止的等待者约 150.24ms 后才成功返回。

采用有上限的加载 context 和 DoChan + select 调用方取消；不要为每个等待者新建无界 goroutine，也不要无界后台继续加载。多实例再评估有租期/随机退避的分布式合并。不存在的小说/章节需要短负缓存和速率控制；当前 nil 不写缓存，连续无效 ID 仍穿库。

### P04 · 解锁缓存要区分未初始化与确认未解锁

cache.go 的 SISMEMBER=false 不能区分集合不存在和章节未购买。service.go:313-329 对每个未命中章节重新查询该用户在该书的全部解锁索引、批量 SADD，并线性 Contains；已缓存其他章节也照样回源。

优先使用精确 EXISTS 点查并缓存短期负结果，或带初始化标记/用户权益版本的完整集合；购买成功必须同步更新/失效负结果。新方案需要解决 N02 的稳定章节身份。禁止通过负缓存让刚购买用户持续被锁。

### P05 · 发布版本粒度与目录读取应避免全书放大

当前任何 novels UPDATE、每条章节 INSERT/UPDATE/DELETE 都推进全书版本；一次 N 章重导入约触发 2N 次小说行更新，价格批量更新也触发版本写放大。一章改动导致全书正文缓存命名空间切换，旧版本正文仍保留约 2–2.4 小时；目录又是整表返回、逐章计算价格。

结合 N01 改成发布 manifest 版本 + 独立章节内容 hash；批量发布每书一次状态切换。目录分页/分段或返回轻量静态元数据，商业规则和权益单独覆盖。测试关注导入锁持有时长、版本数、缓存驻留、批量更新 WAL 和冷启动回源量。

### P06 · 进度同步减少 2N 次往返

shelf/service.go 逐条 GetProgress 再 SaveProgress，而最终 UPSERT 已原子比较时间。可在完整预校验后按 novel ID 合并最新更新，用 UNNEST/pgx batch 批量条件 UPSERT，减少冗余 SELECT。单条 SQL 内必须先去重，避免同一冲突键在一次 INSERT 中被更新两次。保持短事务和批量上限。

### P07 · 请求、回源与连接资源分开限额

25 个 Reader 连接和 15 个 CMS 连接是每实例值，扩容后还叠加任务和运维进程。按数据库总预算设置前台/后台并发、连接池等待指标；缓存故障时用有界回源及短熔断保护数据库。索引前后的查询成本、连接持有时间比单纯调大 MaxConns 更重要。Redis startup/ready 的依赖语义也应明确，缓存故障不能把“可回源”变成无界洪峰。

### P08 · 保留已正确的扣币事务，补完整的并发验收

实际新增探针：32 个相同章节请求，1 次成功、31 次 AlreadyUnlocked，500→450，仅一条解锁；再用 20 个不同章节争抢余额，9 次成功、11 次不足，最终 0。当前钱包行锁、事务内再次查权益及唯一约束有效，不能为降低锁竞争而拆开扣费/权益提交。

后续压测增加：同用户多标签、充值/退款/订阅与扣费交错、目录变更、提交响应丢失、跨实例重复请求。报价/章节元数据读取在事务外；发布并发要结合稳定章节/报价版本核验，否则不能证明“确认的购买对象”和最终内容一致。

## 5. 建议处理顺序及验收范围

1. **先处理 P1**：不可变正文及原子发布、稳定章节购买身份。两者共同决定“买了什么、读到什么”。
2. **可并行的小修**：N03/N04/N05、N07/N08/N09，并补回归；不要只改文档上限来绕过实际列定义。
3. **发布与数据库工作**：N06；SQL 专项优先补 VIP 有效期、整本部分索引、流水首页、Outbox、会话用户索引，再评估目录索引及队列改写。
4. **性能阶段**：先完成正确性与索引，再合并读上下文、正文/预览分离、目录分段、批量进度、并发治理。每一步用同一数据分布和负载模型比较。

最低压测矩阵：匿名预览/VIP/整本/单章命中/未购买各类请求；热点书与随机书；暖/冷/不可用 Redis；大目录；单用户重复与多用户独立扣费；CMS 发布与付款任务同时运行。采集 P50/P95/P99、错误率、SQL 次数与耗时、pool acquire/wait、缓存命中/回源、锁等待、WAL/IO、Outbox 最老年龄。没有本次实测生产 QPS 或容量结论。
