## 4. 首轮确认的遗漏及修复建议

### V01 · P2 · 过期 JWT 被降为匿名，阅读失败不能触发自动续期

**位置**：`reader-backend/internal/auth/middleware.go:50-60`；`reader-backend/internal/novel/handler.go:152-158,176-183`；`reader-backend/internal/novel/read_snapshot.go:51-55`；`reader-front/src/utils/api.ts:91-98,304-305`。

`OptionalClaims` 将无 Authorization 与存在但解析失败/过期的 Bearer 都返回 nil。正文请求随后以匿名身份读取快照；H5 正常携带的 `?user_id=<当前账号>` 与匿名 0 不符，服务端返回 `409 account_changed`。客户端只有收到 401 才执行 singleflight refresh，409 路径不会续期。

**复验**：隔离 PostgreSQL 中保存用户及仍有效的 session，以正确签名、正确 issuer/audience、已过期的 JWT 请求真实 Gin 正文路由。返回：

```text
HTTP 409
{"code":"account_changed","error":"The signed-in account changed. Reload before reading."}
```

没有刷新页面或另一个受保护接口触发续期时，用户继续阅读会失败。目录请求不带 expected user ID 时则可能静默按匿名权限返回。此项不是越权泄露，但会影响付费用户阅读可用性。

**建议**：区分“没有凭据”和“提交了无效/过期凭据”。无凭据继续允许匿名预览；提交了需要续期的无效/过期 Bearer 时返回 401，让现有刷新流程重试；有效账号确实与 expected user ID 不同时才返回 409。保持数据库实时会话/封禁校验及账号隔离，不能通过忽略 expected user ID 解决。

**关闭条件**：经实际 Handler + H5 请求层验证，过期 JWT 且刷新凭据有效时刷新一次并重试成功；刷新失败、真正切换账号、撤销 session、封禁、匿名请求分别符合约定，且不增加每次有效阅读的重复数据库鉴权。

### V02 · P2 · 本地 outbox 读取失败被当作空队列，自动重试停止

**位置**：`reader-front/src/utils/useProgressOutbox.ts:15-16,70-94`；恢复入口 `reader-front/src/App.tsx:690-698`。

`pending()` 使用 `progressOutbox.list(owner).catch(() => [])`。当进度已成功持久化、内存副本已移除，后续 IndexedDB 读取暂时失败时，同步器得到空数组并走成功分支，把 retry 清零；没有新的 queued 事件便不再安排重试。本地恢复也可能把读取失败视作无待同步进度，只恢复服务器旧版本。

**复验**：对当前实际 Hook 源码做转译后执行故障注入，替换 React 挂载及定时器环境，模拟“本地已有 1 条持久进度，第一次 list 抛错，后续可恢复”。首次定时 flush 结束后：

```text
持久待同步记录 = 1
list 调用 = 1
HTTP 发送 = 0
后续定时重试 = 0
```

记录没有被删除，但需要新进度、页面可见性/online 事件或重开等外部唤醒才有机会继续。该探针验证实际 Hook 控制流，不等同于真实浏览器 IndexedDB 故障实验。

**建议**：不要将存储读取失败转换成“确认空队列”。让同步器能够识别失败并进入已有有界退避，同时保留内存数据；恢复入口单独处理“本地状态暂不可读”，不要误确认恢复完成。可返回带存储错误状态的结果，或传播错误并在同步和恢复调用方分别显式处理；不能只删 catch 后留下未处理 Promise。

**关闭条件**：覆盖 list 暂时失败后自动恢复、put 失败的内存兜底、ack 失败后安全重发，并补齐离线/503、部分批次成功、发送中新版本、页面重开、切账号与多标签真实 outbox 回归；确认只删除服务端已确认的所属账号版本。

### V03 · P2 · OSS 相同正文重导入仍全量上传及改写引用

**位置**：`cms-backend/internal/novel/publication.go:57-75`；`cms-backend/internal/novel/publication_repository.go:109-120`；`BulkImportChapters` 调用 `stageChapters` 的路径。

每次 stage 都为全部章节分配带新 UUID 的不可变对象键并上传。即使稳定 ID、位置、正文内容及 hash 都不变，对象键也变化，导致 UPSERT 的 `IS DISTINCT FROM` 对象键条件始终成立。原对象转 retired，新对象转 published，仍产生全书 OSS 上传、章节行更新及清理队列/WAL 放大。

**复验**：真实 CMS Service + Repository + 隔离 PostgreSQL + 模拟 OSS，连续导入相同的两章 TXT。稳定章节 ID 保持不变，正文对象记录从 2 增至 4；第二次提交后为 2 个 retired、2 个 published。与源码逐章重新生成 UUID/上传的行为一致。

内容 hash 缓存和一次目录版本切换已经改善 Reader 回源与版本放大，本项不否定它们，也不代表正文发布原子性失效；但性能验收说明中的“同位置未变化记录跳过更新”在 OSS 路径尚不成立。

**建议**：导入比对时携带已有稳定章节、hash、预览和已发布对象引用。相同内容复用已发布的不可变对象，只为新增/变化正文 stage/upload；仅标题、顺序等元数据变化时保留正文对象。发布事务需要同时支持“新 staged 对象”与“复用 published 对象”，保留版本校验、引用保护和清理 fencing，避免误退役或清理仍被引用的对象。不能恢复固定键覆盖来减少上传。

**关闭条件**：同位置同内容重导入的 OSS PUT 数、正文对象新增数和未变化章节 UPDATE 数均为 0；只改一章仅上传一章；移动/改标题不重复上传正文。再验证上传失败、Commit 失败、并发导入与清理交错不破坏 N01/N02 的保证。
